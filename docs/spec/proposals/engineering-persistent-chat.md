Дата: 2026-11-05. Автор: инженерия (режим plan-eng-review). Статус: **предложение**, ТЗ v1.0 не меняет. Решает основатель (предлагаю новый вопрос **Ф-21**, раздел 8).

## 1. Как я понял идею

Слова основателя: «Чат внизу на любом экране. Открыт экран с заметками — ИИ их сортирует, переставляет. Перешёл на экран расходов — тот же чат, он помнит контекст всех экранов и может взять информацию с любого. Сначала у пользователя шаблоны экранов, он выбирает нужные. Один ИИ-чат на все экраны, помнит контекст всех».

Разбиваю на 5 независимых частей — их можно делать и оценивать по отдельности:

| # | Часть | Что это для пользователя |
|---|---|---|
| A | **Постоянная строка чата внизу** | На любом экране внизу поле «Скажите или напишите…» + микрофон. Ответ раскрывается снизу как шторка, экран под ней остаётся. |
| B | **Один разговор на все экраны** | Это один и тот же разговор: сказал на «Заметках» «запомни, что Арман — это ТОО Арман», на «Расходах» это уже известно. Агент «видит», на каком экране человек сейчас. |
| C | **Экраны из шаблонов** | Каталог: «Заметки», «Дела», «Расходы», «Документы / КП», «Покупки»… Человек включает нужные; порядок экранов настраивается. Позже агент сам предлагает экран («У вас 40 чеков — сделать экран „Расходы“?»). |
| D | **ИИ переставляет и группирует на текущем экране** | «Разложи заметки по темам», «наверх — срочное», «сгруппируй расходы по категориям» → экран меняется сразу, внизу «Отменить». |
| E | **Экран «Расходы»** | Новая функция: ввод трат голосом/текстом, из чеков и скриншотов, итоги по категориям и месяцам. Сейчас в MVP её нет (Kaspi — «после MVP»). |

Главное различие, которое нужно зафиксировать: **экран — это «вид» на общую память, а не отдельная папка**. Запись (например, фото чека) живёт в одной памяти и может одновременно показываться на «Расходах» и «Документах». Тогда идея не ломает «одна память над всем» и поиск по всему.

## 2. Честное мнение

### 2.1 Что хорошо
- **A и B — сильная идея, и почти бесплатная технически.** У нас уже есть `/commands` и `/ask` с параметром `collection_id` («вопрос внутри стопки»), S07/S08 — отдельные полноэкранные «голос/ответ». Постоянная строка внизу — это переупаковка того же, понятная людям, которые знают ChatGPT. Для 45+ «одно место, куда говорить» — плюс: не нужно помнить, где кнопка.
- **D — естественное продолжение «Notion AI, который сам всё организует»** (формулировка основателя). Перестановка по команде — внутреннее и отменяемое действие, полностью укладывается в нашу модель `actions` + `inverse`.
- **«Помнит контекст всех экранов»** реалистично — но не так, что «всё лежит в голове у модели», а через поиск и сводки (раздел 4). Это та же механика, что уже заложена в F-07/F-08.

### 2.2 С чем я не согласен или что вижу риском
1. **C прямо задевает решение №10 «никаких разделов, один агент сам всё раскладывает».** Шаблоны «Заметки / Расходы / Дела» — это и есть разделы, только выбранные самим человеком. Решение основателя я не меняю — оба его слова можно совместить так: **экраны — опциональные «виды», агент сам раскладывает записи по экранам, человек ничего не обязан сортировать**. Но это надо явно подтвердить (Ф-21): либо «экраны дополняют №10», либо «экраны заменяют №10». Инженерно — разные объёмы работы.
2. **Пересекается со «Стопками» (F-09) и тремя вкладками дизайна (Главная · Найти · Дела).** Если делать экраны и стопки параллельно — получится две похожие сущности, люди запутаются. Предлагаю: экран = «закреплённая стопка с шаблоном полей»; авто-стопки живут *внутри* экранов как группы. Это экономит работу, но требует правки дизайна (S06, S09, S11, навигация).
3. **«Расходы» — новая большая функция, а не экран.** Чтобы итоги были точными, нужны структурные поля (сумма, валюта, категория, дата), разбор чеков, повторы трат, категории, правки. Это 2–3 недели и новая зона ошибок (неверная сумма = потеря доверия). В Core сейчас главный путь — КП отца; «Расходы» его отодвинут.
4. **Kaspi автоматически подключить нельзя** (раздел 6.3). Если основатель ожидает «расходы сами подтягиваются из Kaspi» — этого не будет; будет «поделиться чеком / выпиской / вставить текст».
5. **Один разговор + tool calling увеличивают риск prompt injection**: модель, которая и читает чужие документы, и вызывает инструменты «переложить/удалить», опаснее модели, которая только отвечает. Меры — в 4.6.
6. **Стоимость**: длинный общий разговор при неаккуратной сборке контекста дорожает линейно с историей. С мерами из раздела 7 укладываемся в цель «медиана ≤ $1/мес», без них — нет.

### 2.3 Сроки (к Core 11–13 нед., один разработчик с ИИ-агентами) [оценка]

| Часть | Добавит | Можно убрать/заменить | Нетто |
|---|---|---|---|
| A. Строка чата на всех экранах + шторка ответа (вместо S07/S08 как отдельных экранов) | +1 нед. (mobile) | −0,5 (S07/S08 упрощаются) | **+0,5** |
| B. Один разговор: `conversations`, сборка контекста, сводка разговора, единый `POST /chat` с инструментами вместо `/ask`+`/commands` | +2 нед. | −0,5 (`/commands` и `/ask` становятся внутренними путями) | **+1,5** |
| C. Экраны: модель данных, каталог шаблонов как данные, универсальный рендер экрана (список/таблица/доска), sync, порядок экранов, онбординг-выбор | +2,5 нед. | −1 (стопки v1 упрощаются до групп внутри экрана; S11 сливается) | **+1,5** |
| D. Перестановка/группировка патчем + Undo + конфликты офлайна | +1 нед. | — | **+1** |
| E. Расходы: поля, ввод голосом/текстом (код + ИИ), чек/скриншот → поля, вставка текста SMS/push, категории, итоги кодом, повторы трат | +2,5 нед. | — | **+2,5** |
| Созданные агентом экраны / свои шаблоны пользователя | +1,5 нед. | — | **+1,5** |

Итого все части в Core: **≈ +8,5 нед. → Core 19–22 нед.** Это фактически весь бюджет Full. Слишком много для первой проверки на семье.

### 2.4 Варианты (решает основатель)

| Вариант | Что входит в Core | Core | Что дальше |
|---|---|---|---|
| **1. Минимальный** | A + B (чат везде, один разговор, помнит всё). Экраны = существующие вкладки | **13–15 нед.** (+2) | C, D, E — в Full |
| **2. Рекомендую** | A + B + C (только системные шаблоны: «Заметки», «Дела», «Документы/КП»; выбор и порядок экранов) + D | **15–17 нед.** (+4,5) | **E «Расходы» — первым в Full (нед. 15–17)**, затем экраны от агента и свои шаблоны |
| **3. Всё сразу** | A–E + экраны от агента | **19–22 нед.** (+8,5) | Full сдвигается на 25–30 нед. |

Почему вариант 2: он сохраняет суть идеи (один чат везде, шаблоны экранов, ИИ переставляет), а «Расходы» — самую рискованную часть — выпускает, когда модель экранов уже проверена на семье. Модель данных закладываем сразу так, чтобы «Расходы» добавились **как новый шаблон, без миграции** (раздел 3). Если для основателя «Расходы» — главное в идее, разумный обмен: в варианте 2 поменять местами «Расходы» и «Документы/КП-экран» нельзя (КП — для отца, волна 3), но можно «Расходы» в Core ценой переноса импорта Telegram (нед. 8) в Full — тогда Core ≈ 16–18 нед.

Уверенность сроков после изменения падает с ~65–70% до ~55–60%: новая навигация и общий разговор — то, что придётся переделывать после первых пользователей.

## 3. Модель данных

Принципы: (1) запись (`items`) остаётся единственной единицей памяти — поиск, повторы, корзина, источники работают как есть; (2) экран — типизированный вид на записи; (3) шаблоны — **данные с версией**, не код, — новый шаблон приходит с сервера без обновления приложения; (4) структурные поля, по которым считаются деньги, — в типизированных таблицах, а не только в `jsonb`.

### 3.1 Каталог шаблонов — `screen_templates` (данные, версия неизменяема)

| Поле | Назначение |
|---|---|
| `key` | `notes`, `tasks`, `documents`, `expenses`, `shopping`, … или `user:<uuid>` / `agent:<uuid>` |
| `version` | целое; версия неизменяема (как `doc_templates`); экран фиксирует `template_version` |
| `owner` | `system` \| `user` \| `agent` |
| `status` | `draft` \| `published` \| `deprecated` |
| `title {ru,kk}`, `description {ru,kk}`, `icon` | для каталога (KK — только вычитанные строки, R-39) |
| `facet` | какой «аспект» записи нужен: `note` \| `task` \| `document` \| `expense` \| `custom` |
| `fields_schema jsonb` | JSON Schema полей (для `custom`); типы только из белого списка: `text`, `long_text`, `number`, `money` (сумма+валюта), `date`, `datetime`, `enum`, `tags`, `bool`, `person`, `link` |
| `layout` | `list` \| `table` \| `board` (колонки по enum) \| `calendar` \| `builtin:kp` \| `builtin:reminders` |
| `default_view jsonb` | сортировка, группировка, фильтры по умолчанию |
| `aggregates jsonb` | определения итогов: `[{id:"month_total", measure:"sum(amount)", group_by:["currency"], period:"month"}]` — исполняет код |
| `auto_rule jsonb` | правило «какие записи сюда попадают» (envelope `type in (receipt)` / наличие аспекта) |
| `ai_hints_ref` | ссылка на версионированный фрагмент промпта (`prompts/screens/expenses.v1.md`) |
| `min_app_version` | если `layout` требует нового компонента |

Каталог хранится в БД, редактируется миграцией/админ-скриптом, отдаётся `GET /screen-templates` с ETag; телефон кэширует. Системные шаблоны для старта: `notes`, `tasks` (поверх `tasks`/`reminders`), `documents` (поверх `documents`, `layout=builtin:kp`), в Full — `expenses`, `shopping`.

### 3.2 Экраны пользователя — `screens`

`id`, `public_id`, `client_id`, `user_id`, `template_key`, `template_version`, `title`, `title_kk`, `icon`, `position` (дробный индекс, строка LexoRank — порядок экранов), `view_state jsonb` (текущая сортировка/группы/фильтры; `groups: [{key,title,order}]`), `view_version int` (растёт при каждом изменении вида — база для конфликтов, раздел 5), `rule jsonb` (копия/уточнение `auto_rule`), `created_by` (`onboarding` \| `user` \| `agent`), `action_id`, `hidden_at`, `last_opened_at`, `seq`, `created_at`, `updated_at`, `deleted_at`. Лимит `screens.max_per_user` = 20 [предложение].

Решение по «Стопкам»: `collections` остаются (для повторов, сделок, авто-групп), получают `screen_id nullable` — стопка показывается как группа внутри экрана. Альтернатива — слить `collections` и `screens` в одну таблицу (меньше таблиц, но смешивает «вид с полями» и «авто-группу»); рекомендую отдельные таблицы.

### 3.3 Записи на экранах — `screen_items` (многие-ко-многим)

`screen_id`, `item_id`, `position` (LexoRank, nullable = порядок по `view_state.sort`), `group_key` (группа, назначенная ИИ или человеком), `pinned bool`, `added_by` (`rule` \| `agent` \| `user`), `removed_by_user_at` (→ `user_habits.kind=screen_exclusion`, больше не кладём), `updated_at`, `updated_by` (`user` \| `agent`), `seq`; PK(`screen_id`,`item_id`).
Одна запись может быть на нескольких экранах (чек — «Расходы» и «Документы»). Удаление записи — в корзину для всех экранов (R-33); «убрать с экрана» — только связь.

### 3.4 Аспекты записи (типизированные поля)

- `note` — сам `items` (`text`, `title`, `envelope.topics` как теги). Новой таблицы нет.
- `task` — существующие `tasks` / `reminders`.
- `document` — существующие `documents` / `document_versions`.
- **`expense` — новая таблица `expense_entries`** (деньги нельзя считать по `jsonb` и тексту модели):
  `id`, `public_id`, `client_id`, `user_id`, `item_id` (запись-источник: голос, фото чека, вставленный текст; nullable для ручного ввода — тогда создаётся `items.kind=note` с текстом траты), `amount numeric(14,2)`, `currency char(3)` (default `KZT`), `spent_on date`, `spent_at timestamptz nullable`, `category_id`, `payee`, `payee_norm`, `method` (`cash` \| `card` \| `kaspi` \| `transfer` \| `other` \| null), `direction` (`expense` \| `income` \| `refund`), `note`, `source` (`typed` \| `voice` \| `receipt_ocr` \| `receipt_qr` \| `pasted_text` \| `statement_pdf`), `parse_source` (`rules` \| `llm` \| `user_edit`), `review_fields jsonb` (сумма — **всегда** «Проверьте», R-36), `dedup_key` (hash `amount|spent_on|payee_norm`), `line_items jsonb nullable` (позиции чека), `seq`, `created_at`, `updated_at`, `deleted_at`.
  Индексы: `(user_id, spent_on)`, `(user_id, category_id, spent_on)`, `(user_id, dedup_key)`.
- `expense_categories`: `user_id`, `key`, `title`, `title_kk`, `icon`, `parent_id`, `created_by` (`system` \| `user` \| `agent`), `hidden_at`. Старт — ~12 системных («Продукты», «Транспорт», «Коммуналка», «Здоровье», «Дети», «Кафе», «Связь», «Одежда», «Дом», «Подарки», «Работа», «Другое»).
- `custom` (свои/агентские шаблоны) — `item_facets`: `item_id`, `screen_template_key`, `template_version`, `data jsonb` (валидируется `fields_schema` кодом), `review_fields`, `updated_by`, `seq`. Итоги по `number`/`money`-полям — SQL с приведением типов (на наших объёмах достаточно).

### 3.5 Экраны, созданные агентом

- Из системного шаблона: инструмент `create_screen_from_template` → internal action `create_screen` с `inverse` → сразу с «Отменить» (как создание стопки, R-31). В режиме `ask` агент *сам по себе* не создаёт экран — только предлагает (`suggestions.kind=data_proposal`, `key=screen_offer`); по прямой просьбе человека — создаёт сразу.
- Новый шаблон от агента (`owner=agent`): модель возвращает **только** `fields_schema` из белого списка типов, ≤12 полей, без формул; код валидирует, создаёт `screen_templates(status=published, owner=agent)` для этого пользователя. Итоги — только из предопределённых функций (`sum`, `count`, `avg`, `min`, `max` по `number`/`money`). Это Full.

### 3.6 Новые виды действий и операции отмены

`actions.kind` += `create_screen`, `hide_screen`, `delete_screen`, `reorder_screens`, `screen_view_change`, `screen_reorder_items`, `screen_add_item`, `screen_remove_item`, `facet_edit`, `create_expense`, `edit_expense`, `bulk_create_expenses`.
Белый список `inverse` += `restore_view_state`, `restore_positions` (список `{screen_item, position, group_key, base_updated_at}`), `remove_screen_item`, `add_screen_item`, `restore_facet`.

### 3.7 Синхронизация и офлайн
`screens`, `screen_items`, `expense_entries`, `expense_categories`, `item_facets`, `conversation_messages` (последние N) — в `GET /sync`; SQLite-зеркала на телефоне. Каталог шаблонов — отдельно по ETag. Экран открывается мгновенно из локальной БД; итоги расходов считаются **и на телефоне** (та же формула, общий набор тест-векторов, как с парсером дат) — офлайн видно «за ноябрь 84 500 ₸».

## 4. Один чат на все экраны

### 4.1 Сущности

**conversations**: `id`, `public_id`, `user_id`, `kind` (`main`; резерв на будущее), `summary text` (свёрнутая история), `summary_upto_msg_id`, `summary_version`, `msg_count`, `updated_at`; `UNIQUE(user_id, kind)` — один основной разговор.
**conversation_messages**: `id`, `public_id`, `client_id`, `conversation_id`, `user_id`, `role` (`user` \| `assistant` \| `tool`), `screen_id` (где сказано), `input_kind` (`typed` \| `voice` \| `share`), `content` (текст; голос — после STT), `tool_calls jsonb`, `tool_results_ref jsonb` (ссылки, не копии данных), `citations jsonb` (`[{screen_id,item_id,chunk_id}]`), `action_ids`, `pending_action_ids`, `ai_generated`, `prompt_version`, `cost_usd`, `created_at`, `deleted_at`.
Это персональные данные: хранятся в КЗ, входят в экспорт (F-26) и удаление аккаунта (F-27); «Очистить историю чата» в настройках; сообщения, превратившиеся в записи, остаются записями. Срок хранения — как у записей [на подтверждение B/юриста].

### 4.2 Как он «помнит все экраны» — слои памяти

Не «всё в промпт», а сборщик контекста (`chat/context.py`) с жёстким бюджетом токенов на каждый слой:

| Слой | Что | Как получается | Бюджет [оценка] |
|---|---|---|---|
| 1. Системный промпт + описания инструментов | правила агента, R-36, маскировка, формат цитат | статичный файл с версией; **кэшируется** провайдером | ~3 000 (кэш) |
| 2. Профиль и привычки | имя, язык, tz, активные `user_habits` (алиасы «мама = Гульнара», «Магнум → Продукты») | код, топ-20 по `last_used_at` | ≤400 |
| 3. Индекс экранов | все экраны: имя, шаблон, число записей, 1 строка итогов | код (`screen_summaries`, без ИИ) | ≤30 на экран, ≤600 |
| 4. Текущий экран | шаблон, вид (сортировка/группы), видимые записи: `id`, заголовок, ключевые поля | код из того, что на экране сейчас (телефон присылает `screen_id` + `visible_item_ids` + `view_version`) | ≤1 500 (≤40 записей) |
| 5. Свёрнутая история разговора | факты и договорённости из прошлых реплик | `CHAT_SUMMARIZE` (лёгкая модель), раз в ~10 реплик или при переполнении слоя 6 | ≤600 |
| 6. Последние реплики | дословно | последние 6–10 сообщений, пока влезает | ≤2 500 |
| 7. Найденное по всем экранам | фрагменты записей под текущий вопрос | существующий RRF (6.9) по **всем** записям; буст +текущий экран; `<untrusted_data>` + маскировка | ≤8 фрагментов, ≤2 500 |

Итого вход ~8–11 тыс. токенов на шаг, из них ~3 тыс. кэшируется. Слой 7 заполняется **только если нужен** (`QUERY_PLAN` или код решили, что вопрос о данных); иначе модель может сама вызвать `search_items`.

`screen_summaries` (кэш, считает код при изменении экрана и ночью): `screen_id`, `item_count`, `last_titles[5]`, `aggregates jsonb` (для расходов: итог месяца по валютам, топ-3 категории), `updated_at`. Никакого ИИ — бесплатно и всегда точно.

Устойчивые факты, которые человек явно сказал в чате («Арман — это ТОО Арман», «траты на бензин — рабочие»), пишутся не в историю, а в `user_habits` (`source=user_explicit`) — тогда они не теряются при свёртке истории и видны в «Что я для вас настроил» (S30) с возможностью удалить.

### 4.3 Инструменты (tool calling)

Модель **не исполняет** ничего сама (правило 5.7 п. 2 сохраняется): она возвращает вызовы, код проверяет их по схеме и белому списку и исполняет.

| Инструмент | Тип | Что делает код |
|---|---|---|
| `search_items(query, screen_id?, kind?, from?, to?)` | чтение | RRF по всем записям; возвращает id + фрагменты |
| `get_items(ids)` | чтение | карточки (с маскировкой) |
| `list_screen(screen_id, sort?, filter?, limit≤50)` | чтение | содержимое любого экрана |
| `aggregate(screen_id\|facet, measure, group_by?, period?, filters?)` | чтение | **SQL кодом**; возвращает числа + id записей-оснований; модель числа не считает |
| `create_item(screen_id?, text, fields?)` | внутреннее | запись + привязка к экрану; поля — валидация схемой |
| `update_item_fields(item_id, patch)` | внутреннее | JSON Patch только по полям схемы; сумма → снова «Проверьте» |
| `add_to_screen / remove_from_screen(item_ids, screen_id)` | внутреннее | связи `screen_items` |
| `move_items(item_ids, from, to)` | внутреннее | = remove + add одним action |
| `set_view(screen_id, sort?, group_by_field?, filters?)` | внутреннее | меняет `view_state` (дёшево, без перечисления записей) |
| `propose_reorder(screen_id, base_view_version, groups?, order?)` | внутреннее | патч раздела 5 |
| `create_screen_from_template(template_key, title?)` | внутреннее | экран + action |
| `create_expense(amount, currency, date_text, category?, payee?, method?)` | внутреннее | `Decimal`, дата — кодом, категория — код/привычки |
| `create_reminder`, `create_task`, `kp_*`, `draft_message` | как сейчас | через существующие пути; внешнее → `pending_actions` |
| `delete_items(ids)` | внутреннее, с ограничением | корзина 30 дн.; >5 записей — подтверждение «Да» |

Правила цикла: ≤4 шага инструментов на одну реплику человека (`chat.max_tool_steps`); параллельные чтения разрешены; запись — последовательно. Все внутренние изменения одной реплики = **одно** действие в «Что я сделал» с одной кнопкой «Отменить» (например, «Разложил 23 заметки на 5 групп · Отменить»). Явная просьба человека («разложи») выполняется сразу с «Отменить» в любом режиме автономии; собственная инициатива агента — по правилам R-31 (в `ask` — только предложение).

Адаптеры (5.5) нормализуют tool calling: Anthropic tools / OpenAI function calling / Gemini functionDeclarations — одна внутренняя схема `ToolSpec`. Bake-off нед. 0 расширяется: 30 диалогов с инструментами (RU/KK) — точность выбора инструмента и аргументов на лёгкой модели. Переключение провайдера в середине шага — только до первого токена или вызова (как 5.3).

### 4.4 Цитаты и источники
- Цитата = `{screen_id, item_id, chunk_id?}`; в UI — чип «Расходы · Чек Magnum, 3 ноя» или «Заметки · голосовое, 12 окт» → тап открывает запись (S09) на её экране.
- Цитировать можно только id, которые вернули инструменты в этом шаге (5.6 п. 5).
- Проверка чисел (5.6 п. 4) расширяется: число в ответе должно найтись в процитированных фрагментах **или в результате `aggregate`**; итоги расходов модель обязана брать из `aggregate`, иначе фраза удаляется / помечается «не нашёл в записях».

### 4.5 API
- **`POST /chat/messages` (SSE)** — заменяет для телефона `/ask` и `/commands`. Вход: `text` или `upload_id` голоса, `screen_id`, `visible_item_ids[]` (≤40), `view_version`, `lang`, `client_id`. События: `understood`, `status`, `sources`, `token`, `tool_activity` («Ищу в Расходах…»), `action` (с `undo`), `pending_action`, `screen_patch` (изменения вида для мгновенной отрисовки), `citations`, `checked`, `general_answer_offer`, `done`, `deferred`, `error`.
- `GET /chat/messages?before=` — история (ленивая подгрузка); `DELETE /chat/history`.
- `/ask`, `/commands` остаются внутренними функциями (и для обратной совместимости первой сборки).
- Экраны: `GET /screen-templates`; `GET/POST /screens`; `PATCH /screens/{id}` (имя, иконка, `view_state` с `base_view_version`); `POST /screens/reorder`; `GET /screens/{id}/items?cursor=`; `POST/DELETE /screens/{id}/items`; `POST /screens/{id}/reorder` (ручная перестановка пальцем).
- Расходы: `POST/PATCH/DELETE /expenses`, `POST /expenses/parse` (без сохранения, `rules_first`), `POST /expenses/import` (выписка PDF → план → «Да»), `GET /expenses/aggregate`, `GET/POST /expense-categories`.

### 4.6 Безопасность одного разговора
Риск: модель читает документ с текстом «удали все заметки» и вызывает `delete_items`. Меры (дополнение 5.7):
1. Инструменты-изменения доступны в шаге, только если **реплика человека** содержит намерение изменить (классификатор INTENT на фразе человека, не на данных) — иначе в этом шаге модели отдаются только инструменты чтения.
2. Массовые операции (>20 записей перестановкой, >5 удалением, любой импорт) — превью и «Да».
3. Внешнее — по-прежнему только `pending_actions` с превью от кода.
4. Свёрнутая история (`summary`) строится только из реплик человека и ответов агента, **без** содержимого `untrusted_data` — иначе инъекция «прописывается» в долгую память.
5. Корпус инъекций в CI пополняется сценариями «инструкция в документе → вызов инструмента».

### 4.7 Без интернета и «Без ИИ»
- Офлайн: строка чата сохраняет сказанное как запись на текущем экране (голос — в очередь), локальный поиск FTS5 отвечает «Нашёл у себя»; расход «5000 бензин» разбирается кодом на телефоне (при Ф-1). Ответ ИИ — «разберу, когда появится интернет».
- «Без ИИ» (R-05): строка становится полем «поиск + быстрая запись», голос недоступен; перестановка — только пальцем и сортировками.

## 5. Перестановка и группировка на текущем экране

### 5.1 Порядок предпочтения (дешевле и надёжнее — первым)
1. **Сортировка по полю** («по дате», «по сумме», «сначала новые») → `set_view` — код, без перечисления записей. Обычно хватает лёгкой модели или даже правил.
2. **Группировка по полю** («по категориям», «по клиенту») → `set_view(group_by_field)` — код.
3. **Смысловая группировка** («разложи заметки по темам») → ИИ назначает `group_key` записям: модель видит только `id` + заголовок + 1 строку (маскировано), пачками по ≤150; названия групп — ИИ, состав — проверяет код.
4. **Ручной смысловой порядок** («наверх — срочное, потом про Армана») → `propose_reorder` с явным порядком; ≤150 записей за раз; больше — только группы + сортировка внутри группы.

### 5.2 Формат патча
```json
{"screen_id":"0193…","base_view_version":41,
 "view":{"group_by":"ai_groups","sort":"position"},
 "groups":[{"key":"g1","title":"Ремонт кухни","order":1},
           {"key":"g2","title":"Клиент Арман","order":2}],
 "assign":[{"item":"0193…a1","group":"g1"},{"item":"0193…b2","group":"g2"}],
 "order":{"g1":["0193…a1","0193…c3"]}}
```
Валидация кодом: все id принадлежат экрану; ни одна запись не потеряна и не задвоена (не вошедшие → группа «Остальное»); ≤12 групп; названия ≤40 символов, RU/KK по языку. Позиции переводятся в LexoRank (меняются только затронутые строки).

### 5.3 Применение и Undo
- Перестановка — внутреннее и отменяемое действие → **применяется сразу** с анимацией и полосой «Разложил 23 заметки на 5 групп · Отменить» (та же логика, что R-30 для КП). Предпросмотр «Применить?» — только для массовых (>150 записей) или если человек включил «Спрашивать перед перестановкой» (`user_habits`).
- `actions(kind=screen_reorder_items)`, `inverse = restore_view_state + restore_positions` (старые `position`, `group_key` каждой затронутой записи). Отмена 30 дней (R-33), идемпотентна.
- Если после перестановки человек сам передвинул запись — частичная отмена: его перемещения сохраняются, «Часть уже изменена вами — вернул остальное» (существующее правило 3.7).

### 5.4 Конфликты с офлайн-правками
- Каждый экран имеет `view_version`; патч ИИ строится от `base_view_version`, которую прислал телефон.
- На сервере при применении: если `view_version` ушла вперёд (человек офлайн двигал/добавлял) — **rebase**, а не отказ: (а) записи, которые человек двигал после базы (`screen_items.updated_by=user, updated_at > base`), сохраняют его позицию — **человек главнее ИИ**; (б) новые записи после базы — в «Остальное» / по своему полю сортировки; (в) удалённые — выпадают из патча; (г) если затронуто >30% записей — патч не применяется, «Пока я думал, экран изменился — разложить заново?».
- Ручная перестановка пальцем офлайн — обычная мутация в outbox (`client_id`, `base_version`); LexoRank делает перестановку одной записи изменением одной строки, поэтому параллельные правки с двух телефонов почти не конфликтуют; при равных ключах — детерминированный tie-break по `item_id`.
- Офлайн-телефон получает результат ИИ через `sync` как обычные изменения `screen_items` + `screens.view_state`.

## 6. Экран «Расходы» (если включаем)

### 6.1 Ввод
| Способ | Как работает | Без ИИ |
|---|---|---|
| Голос / текст в чате: «потратил 5 000 на бензин», «Магнум 12 400 вчера каспи» | **Код сначала** (как Ф-1): парсер сумм RU/KK («5 тыс», «пять тысяч», «12,4к», «₸/тг/тенге/$/руб»), даты («вчера», «15-го»), способа («каспи», «наличка»); категория — словарь плательщиков + привычки (`alias`: «Магнум → Продукты»); не понял → `EXPENSE_EXTRACT` (лёгкая модель) | да (при Ф-1) |
| Ручная форма | сумма (цифровая клавиатура), категория, дата — 3 поля | да |
| Фото чека / скриншот | OCR (6.1) → `EXPENSE_EXTRACT` → поля + позиции; сумма всегда «Проверьте» (R-36) | частично |
| QR на фискальном чеке КЗ | QR ведёт на страницу ОФД с данными чека; можно открыть ссылку и разобрать (allowlist доменов ОФД, без приватных IP — 5.7 п. 7) | да | 
| Чек из Kaspi / банка через «Поделиться» | Kaspi позволяет поделиться квитанцией платежа/перевода (PDF или картинка) [проверить на актуальной версии] → как PDF/фото | да (PDF) |
| Выписка PDF (Kaspi Gold, Halyk и др.) | Человек скачивает выписку в банковском приложении → «Поделиться» к нам → разбор таблицы (`pdfplumber`) → план «Нашёл 86 операций за октябрь, 4 уже есть» → **одно «Да»** (`bulk_create_expenses`, одна отмена) | да (текстовый PDF) |
| Вставленный текст SMS/push банка | Человек копирует или делится текстом уведомления → парсер по шаблонам банков + `EXPENSE_EXTRACT` | частично |

Повторы трат: `dedup_key` (сумма + дата + плательщик) — «Похоже, эта трата уже есть (из выписки)» [Объединить?]; важно, потому что один платёж придёт и чеком, и выпиской.

### 6.2 Kaspi — честно
- **Публичного API для личных счетов Kaspi нет.** Kaspi Pay / Kaspi Магазин API — для продавцов, к личным тратам доступа не дают.
- **Вход логином/паролем в Kaspi от имени человека («скрейпинг») — нет**: нарушение условий банка, риск безопасности и выглядит как мошенничество для 45+ (та же логика, что в Ф-4).
- **Чтение SMS (`READ_SMS`) — нельзя**: Google Play разрешает его только приложениям SMS по умолчанию; на iPhone доступа к SMS нет вообще. К тому же Kaspi в основном шлёт push, а не SMS.
- **Чтение push-уведомлений банка на Android (`NotificationListenerService`)** — технически возможно, но: чувствительное разрешение (ревью Google Play, раскрытие), видит *все* уведомления, на iOS невозможно. Не для MVP; можно рассмотреть как опцию после MVP с отдельным согласием.
- **Open Banking в РК** (Нацбанк развивает Open API) — для частного приложения на старте недоступно [проверить статус и требования к лицензии]. Это «после MVP» вместе с пунктом «Kaspi/1С» из SPEC.
- Итог: реалистично — **«поделиться квитанцией / выпиской / текстом» + голос + фото чека**. Обещать «траты сами подтягиваются из Kaspi» нельзя — ни в продукте, ни в рекламе.

### 6.3 Валюта и итоги
- Валюта по умолчанию **KZT**, ISO-код хранится у каждой траты; формат «12 500 ₸» (`Intl`, неразрывный пробел); тиыны — до 0,01.
- Итоги — только код (`expenses/calc.py`, `Decimal`, `ROUND_HALF_UP`), по валютам **отдельно**; конвертации в MVP нет (иначе «итог 84 500 ₸» соврёт). Позже — опционально по курсу Нацбанка на дату, с подписью «по курсу НБ РК на 3 ноя».
- Итоги в чате («сколько на продукты в октябре?») → инструмент `aggregate` → модель только формулирует; событие `checked` подтверждает, что число из `aggregate`.
- Возвраты (`direction=refund`) вычитаются; переводы между своими счетами — категория «Переводы», в итог трат не входят по умолчанию.
- Это не финансовый советник: без прогнозов и рекомендаций по кредитам (аналогично R-43).

### 6.4 Приватность
Финансовые данные — персональные; хранятся в КЗ, маскировка карт/IBAN (R-24) уже есть; push по тратам — без суммы без `push_content`. В согласии новых получателей нет (OCR/LLM те же), но в «Как работает помощник» добавить строку о расходах [юрист].

## 7. Стоимость на человека и защита

### 7.1 Оценка шага чата [оценка; цены по прайсу Anthropic на 2026-10, сверить на нед. 0]
Цены: лёгкая модель (Claude Haiku 5.5) $0,10 / $0,50 за 1 млн токенов вход/выход; сильная (Claude Sonnet 5.5) $2 / $10, чтение кэша $0,20. Запасные провайдеры — по bake-off.

| Сценарий шага | Вход / выход | Лёгкая | Сильная |
|---|---|---|---|
| Простая реплика (записать, напомнить) | ~6k / 200 | ≈ $0,0007 | ≈ $0,01 |
| Вопрос по данным с поиском | ~10k / 400 | ≈ $0,0012 | ≈ $0,02 |
| С 2–3 вызовами инструментов (контекст пересылается каждый шаг) | ~25k / 800 суммарно | ≈ $0,003 | ≈ $0,05 |
| Смысловая группировка 150 записей | ~8k / 1,5k | ≈ $0,0016 | ≈ $0,03 |
| Свёртка истории (раз в ~10 реплик) | ~4k / 500 | ≈ $0,0007 | — |

Типичный пользователь — 5–10 реплик в день ≈ 150–300 в месяц: на лёгкой модели **≈ $0,2–0,6/мес**; если 15% шагов уходит на сильную — **+$0,5–1,5/мес**. Вывод: цель «медиана ≤ $1» выдерживается, **только если сильная модель — исключение**. Главный драйвер стоимости — не размер памяти, а (а) доля сильной модели и (б) число шагов инструментов. Если запасной провайдер дороже лёгкой модели — пересчитать.

### 7.2 Защита
1. **Код вместо ИИ** где можно: правила для «записать/напомнить/потратил», `set_view` для сортировок, итоги — SQL, сводки экранов — код. Ожидаемо 30–50% реплик без вызова LLM [оценка].
2. **Жёсткие бюджеты слоёв контекста** (4.2), потолок входа на шаг `chat.max_input_tokens=12000`; история длиннее — только через `summary`.
3. **Кэш промпта**: стабильный порядок `tools → system → профиль`, изменчивое (экран, найденное, реплика) — в конце. Без меток времени в системном промпте.
4. `chat.max_tool_steps=4`; параллельные чтения в одном шаге; повтор одного и того же инструмента с теми же аргументами — запрещён кодом.
5. Эскалация на сильную модель — только по правилам (сравнение >N источников, многошаговое действие, низкая уверенность), не «на всякий случай»; при 80% месячного бюджета — эскалация выключается (как 5.4).
6. Новая задача `CHAT` в классе `answers`, `CHAT_SUMMARIZE` и `EXPENSE_EXTRACT` (из фото) — `background`; лимиты профилей (5.4) не меняются; `provider_usage.task` различает их для дашборда стоимости.
7. Перестановка по смыслу — ≤150 записей за вызов, ≤3 больших перестановки в день в профиле `regular` (`limits.ai_reorder_per_day`).
8. Алерт: пользователь с >60 шагами чата в день или стоимостью шага >$0,05 — в дашборд F-31.
