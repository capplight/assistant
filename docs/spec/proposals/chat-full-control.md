# Чат управляет всем приложением («ИИ понимает — скрипт делает» для всех экранов)

Архитектор, 2026-11-20. Только документ: кода и коммитов нет. Основано на коде
(`src/assistant/chat/*`, `src/assistant/actions/*`, `src/assistant/api/routes/*`, `mobile/src/app/*`)
и контрактах `docs/api/chat.md`, `actions.md`, `today.md`, `calendar.md`, `plans.md`,
`FOUNDER-DECISIONS.md` (Ф-39, Ф-66, Ф-78, принцип 2026-11-17, Ф-86…Ф-89).

**Запрос основателя.** Снять ограничения: всё, что человек может сделать на экранах, он может
попросить в чате — по той же схеме: модель даёт команду, выполняет код. Если просьба не меняет
экраны — помощник отвечает как обычный ИИ-ассистент.

**Повод.** План поездки в Стамбул сохранён заметкой по дням → «добавь в календарь» → не вышло.
Почему: «добавь» — слово изменения (`intent._CHANGE`), ход идёт на Sonnet (`chat_change`) с
инструментами `create / update / move / reorder / create_page_from_template / rename_page`, но
инструмента «в календарь» нет; модель либо пишет «добавляю», либо после `claim_retry` код честно
отвечает «Не получилось — ничего не изменил» (Ф-88 сработал правильно — не хватило возможности).

**Пункт 1 (уже в работе, не переделываем):** план → календарь: добавить шаги/дни плана в календарь,
убрать, сдвинуть — делает backend-программист сейчас. Ниже он считается первой операцией нового
реестра; если его код появится раньше реестра, в фазе 0 он просто переезжает в реестр без смены
поведения.

## 2. Почему сейчас нельзя просто «дописать ещё инструментов»

1. **Логика изменений живёт в роутах.** `api/routes/tasks.py` сам собирает ops
   (`set_task`, `cal.alert_ops`, `cal.reminder_shift_ops`, `linked_reminder_cancels`) и вызывает
   `engine.apply`. Чату пришлось бы копировать это → экраны и чат разойдутся (корзина уже
   разошлась).
2. **Каждый инструмент — это токены в каждом ходе изменения.** Сейчас схемы мутаций (~6 шт.,
   `SetViewArgs` самая большая) ≈ 2–3 тыс. токенов [оценка]. Если добавить ~15 инструментов
   «как есть», ход на Sonnet вырастет на 5–8 тыс. входных токенов → +$0.015–0.025 за ход
   [оценка, без кэша], и модель чаще путает инструменты.
3. **Ссылки на объекты.** Модель видит только записи (`s1…`). Дела, события, траты, напоминания
   как объекты у неё ссылок не имеют — нечем сказать «вот это дело перенести».

## 3. Архитектура: один реестр операций для экранов и чата

### 3.1 Реестр операций (`src/assistant/operations/`, владелец api)

Одна операция = одна функция бизнес-логики, которую вызывают **и** REST-роут, **и** чат.

```text
Operation:
  name        "tasks.set_done" | "tasks.reschedule" | "calendar.move" | "reminders.cancel" | ...
  domain      records | tasks | calendar | reminders | expenses | pages | plans | settings | ...
  args        pydantic-модель (strict): то, что приходит и из REST-тела, и из вызова модели
  risk        safe | bulk | irreversible     (политика подтверждений — §3.4, решает код)
  targets     какие ссылки принимает (t-, e-, c-, r-, s-, p-)
  run(session, user_id, args, by=Initiator.USER|AGENT, now) -> OpResult
OpResult:     ops (для engine.apply), action kind, summary/notice, changes[], touched[]
```

- `run` строит ops и вызывает `engine.apply` (как сейчас), пишет **одно Action с `inverse`**
  через `actions.record`. Undo, «Что изменилось», «Изменил помощник» (Ф-73), группы (step 6) —
  без изменений, всё уже есть.
- **Роуты становятся тонкими**: разобрать тело → `operations.run("tasks.reschedule", args, by=USER)`
  → ответ. Контракты REST не меняются ни на байт (тесты `tests/api/*` — сторож).
- **Чат** вызывает тот же `operations.run(..., by=AGENT)`. Так чат и экраны физически не могут
  разойтись.
- Тест-паритет: для каждой операции один тест «через роут» и «через чат» дают одинаковые ops и
  одинаковое состояние БД.
- Пункт 1 (план → календарь) становится операциями `plans.to_calendar`, `calendar.remove_plan`,
  `calendar.shift_plan` — с тем же кодом, который сейчас пишет программист.

### 3.2 Как модель вызывает операции: доменные инструменты, а не 40 штук и не один «do»

Варианты:
- (a) один инструмент на операцию — 40+ схем, дорого и путано;
- (b) один общий `do(op, args: object)` — дёшево, но схема пустая: провайдер не проверяет
  аргументы, модель угадывает поля → больше ошибок и повторных шагов;
- (c) **рекомендую:** один инструмент на домен (`tasks`, `calendar`, `reminders`, `expenses`,
  `records` = нынешние create/update/move, `pages`, `settings`), внутри — `op` (enum) и
  аргументы как размеченное объединение (`anyOf` по `op`). Это 5–8 инструментов, каждый
  ≈ 300–600 токенов [оценка]. Генерируются из реестра автоматически (описание + схема), руками не
  пишутся.

**Выбор набора на ход — кодом** (как сейчас `make_plan` и `asks_web`): маленький словарь доменов
по словам фразы и по странице («напомин», «будильник» → reminders; «встреч», «календар», время
«в 15:00», «на пятницу» → calendar+tasks; «потратил», «трат», «₸» → expenses; «купил», «купленн»
→ tasks+expenses; «план» + выбранный план → plans+calendar). Ничего не узнали → `records`,
`tasks`, `calendar` (самые частые) + короткая строка-каталог в контексте «Ещё умею: напоминания,
траты, бюджет, страницы — скажи словами». Если модели нужен другой домен, она вызывает
`need_tools(domain)` (лёгкий читающий инструмент), код добавляет домен на следующем шаге —
один дополнительный шаг вместо постоянно раздутого промпта.

**Кэш промпта.** Набор инструментов — часть кэшируемого префикса (`cache_control` уже есть в
`anthropic_adapter`). Порядок инструментов фиксированный (по реестру), наборы — из небольшого
числа комбинаций, поэтому каждая комбинация кэшируется отдельно. Проверить долю попаданий в
`provider_usage` в первую неделю.

### 3.3 Ссылки на объекты и читающие инструменты

- Новые префиксы в `SourceBook`: `t1` (дело/покупка), `c1` (вхождение календаря — дело +
  `occurrence_at`), `e1` (трата), `r1` (напоминание), `p1` (страница — уже есть), `s1` (запись —
  уже есть). Модель называет объекты **только** ссылками, которые ей показали; код переводит в id.
  Неизвестная ссылка → ошибка инструмента, ничего не меняется (как сейчас `_sources`).
- Читающие инструменты (дешёвые, на Haiku тоже доступны): `calendar_range(from, to)` (поверх
  того же кода, что `GET /v1/calendar`), `tasks_list(list, due?, done?)`, `reminders_list(…)`,
  `expenses_list(period, category?)`. Возвращают объекты со ссылками. Для частого случая «это» —
  выбранный объект на экране (`selected_item_id`) уже даёт ссылку.
- Числа и даты из этих инструментов — факты кода: попадают в `env.computed`, `AnswerGate` их
  пропускает (как `aggregate`).

### 3.4 Подтверждения, «Отменить», безопасность — решает код, не модель

| `risk` | Что делает код | Примеры |
|---|---|---|
| `safe` | сразу, notice «… · Отменить» (Ф-66, Ф-75) | отметить, перенести одно событие, исправить трату, удалить в корзину ≤50 |
| `bulk` | `confirm` с числом («Перенести 12 событий на час позже?» [Да] [Не сейчас]), потом одно действие с «Отменить всё» | >10 объектов, слово «все/всё» по делам/календарю/тратам, «убрать купленное» при >10 |
| `irreversible` | компактное «Да» (Ф-66) или 🚫 в чате | удалить навсегда, отправить КП, «забудь всё» |

- Правило намерения остаётся: менять можно, только если **слова человека** просят
  (`rules_first` + INTENT). Расширяем словарь глаголов: «отметь», «перенеси на», «сдвинь»,
  «передвинь», «отмени напоминание», «не напоминай», «исправь сумму», «поставь бюджет»,
  «пропусти» и казахские пары (R-39). Защиты по словам — как `is_delete`: трату нельзя
  удалить/исправить, если во фразе нет такого слова; текст записей и «поделиться» никогда не
  вызывает операцию (уже так в `execute`).
- Лимиты: ≤8 действий на фразу (`MAX_ACTIONS_PER_PHRASE`), ≤50 объектов на вызов — как есть.
- `claim_retry` и честный текст Ф-88 — без изменений; они станут срабатывать реже, потому что
  инструмент найдётся.
- Конфликт с телефоном: операции используют `expect` (как `set_task`), чтобы чат не затёр
  изменение, сделанное человеком офлайн и пришедшее из outbox.

### 3.5 Сначала код, модель — только для непонятного (Ф-78, экономия)

Самые частые фразы разбирает код без модели, как уже сделано для трат и дел со временем:
«хлеб купил» (открытая покупка «хлеб» есть) → `tasks.set_done`; «перенеси <дело> на пятницу / на
16:00» при однозначном совпадении названия → `tasks.reschedule` (`assistant.timewords`);
«не напоминай про <…>» → `reminders.cancel`. Ничего однозначного → модель (Sonnet, `chat_change`).

|---|---|---|---|
| Простая команда, понятая кодом | $0 | $0 | §3.5 |
| Изменение через модель, 1 домен | $0.01–0.03 | $0.012–0.035 | +1 доменный инструмент ≈ +0.5 тыс. токенов; кэш префикса |
| Изменение, 2–3 домена (Стамбул → календарь + напоминания) | не умеет | $0.02–0.05 | наборы по словам; `need_tools` вместо всех |
| Вопрос / обычный ассистент (Haiku) | ≈ $0.001–0.003 | то же | мутаций нет; см. §4 (меньше лишнего поиска) |

Сторож: ежедневный отчёт `python -m assistant.ai.costs report` + новая метрика «доля ходов на
Sonnet» и «среднее инструментов в ходе»; порог — алерт в `ops_alerts`, если средняя цена хода
изменения > $0.04 за сутки.

## 4. «Обычный ассистент»: что сейчас мешает и как исправить

Промпт `chat.v4` (Ф-86) уже разрешает свободные ответы (`mode: general`), и `AnswerGate` не
режет общие ответы. Мешает **маршрут до модели**:

1. **Длинная просьба сохраняется заметкой.** `_ask_intent` при `len > 200`, ≥7 цифр или
   падении модели зовёт `note_by_code`, а она любую фразу из 3+ слов делает заметкой. «Переведи
   на английский: <абзац>», «Сократи этот текст: …», «Посчитай 1 250 000 × 12 %» — станут
   записями в «Заметках». **Исправление:** в `_QUESTION` добавить глаголы просьб к ассистенту
   (переведи, напиши (не «запиши»), сочини, перефразируй, сократи, исправь ошибки в тексте,
   посчитай, вычисли, сравни, объясни, проверь текст, «как сказать», kk-пары) — тогда фраза — вопрос
   ещё до INTENT; длинный текст с таким глаголом в начале — тоже вопрос. `note_by_code` для фраз
   с глаголом-просьбой — никогда не заметка.
2. **INTENT не знает такого класса.** Описание `question` — «спрашивает, ищет, совет, план,
   разговор»; «напиши поздравление маме» Haiku иногда относит к `note`. Добавить в
   `INTENT_SYSTEM`: «asks the assistant to write, translate, rewrite, calculate or explain
   something → question». Новая версия `intent.v2`.
3. **«Исправь …» — уже глагол изменения записи (Ф-73).** «Исправь ошибки в этом тексте: …»
   без выбранной записи и с текстом в самой фразе — это просьба к ассистенту, не правка
   записи. Правило: глагол правки + после двоеточия свой текст и нет «в заметке/это» → вопрос.
4. **Лишний поиск по записям.** Каждый ход собирает записи (`assemble`), даже для перевода.
   Для фраз с глаголом-просьбой и без слов о «моём» — не подтягивать записи в контекст (только
   память, если она про фразу). Дешевле и меньше «У вас в записях…» не к месту.
5. **Статус «Смотрю записи…»** на переводе выглядит странно — для таких фраз «Думаю…».
6. Ограничения длины (3000 токенов, 4000 символов) — для письма/перевода хватает; не трогаем.
7. Веб-поиск (Ф-86/Ф-87) — без изменений: только по `asks_web`, платный, ≤3 поиска, не в ходе
   изменения.
8. Смешанная фраза («перенеси встречу на 16 и подскажи, что подарить Айгерим») — ход изменения
   на Sonnet отвечает и на вторую часть; промпт v5 явно говорит «после изменения ответь и на
   остальное».

Промпт `chat.v5` (новая версия, старую не трогаем): короче раздел «Changes» (правила уходят в
описания доменных инструментов из реестра), явный пункт «writing / translation / math — answer
fully, mode general, nothing is saved unless asked», и короткий каталог «что я умею менять».

## 5. План по фазам

### Фаза 0 — фундамент (≈1 неделя, один backend-программист; не пересекается с пунктом 1)

Backend:
- пакет `operations/`: тип `Operation`, реестр, генерация доменных схем инструментов,
  политика `risk`;
- перенести в операции то, что уже есть: tasks (add/patch/done/delete/clear-done), reminders
  (create/patch/delete), expenses (patch/delete); роуты становятся тонкими; REST-контракты не
  меняются;
- **свести корзину**: `update.trash` в чате для записи дела/траты → `tasks.delete` /
  `expenses.delete` (как экран, со связанным напоминанием);
- ссылки `t/c/e/r` в `SourceBook`; выбор доменов кодом; `need_tools`;
- поле `touched: ["tasks","calendar","reminders","expenses","budget","today","pages"]` в Action
  (новое, необязательное; старые телефоны игнорируют).
- исправления §4 п.1–5 («обычный ассистент») — маленькие, можно отдать отдельно первыми.

Mobile:
- после `action` уже есть `kickSync()`; добавить: по `touched` перезапросить то, что не идёт
  через sync — `GET /v1/calendar` (кэш диапазона), `GET /v1/expenses/budget`, `GET /v1/today`;
- `notice.target.kind`: добавить `calendar` (открыть календарь на дне) и `budget`; неизвестное —
  без перехода.

### Фаза 1 — частые разрывы (P1), ≈1–1,5 недели

- пункт 1 (план → календарь) в реестре;
- `tasks.set_done` / `undone` (включая «хлеб купил» кодом), `tasks.reschedule`;

Mobile: только проверка, что экраны обновились (дела, календарь, расходы, «Сегодня») после

настройки (`me`: язык, пояс), тихие часы, привычки, стопки, порядок вкладок, категории трат,

### Тесты и золотой набор (каждая фаза)

- `tests/operations/`: паритет «роут = чат» для каждой операции; undo-круг
  `apply(apply(x).inverse)`; `expect` против офлайн-правки.
- `tests/chat/`: выбор доменов по словам; ссылки t/c/e/r (неизвестная → ошибка, ничего не
  изменено); bulk → `confirm`; защита словами (нет «удали» → не удаляет трату).
- Золотой набор (`eval/golden/`): +≈60 случаев RU/KK — по 4–6 на операцию фазы 1 («перенеси
  встречу с Ерланом на 16:00», «хлеб купил», «не напоминай про свет», «нет, это было 5000»,
  «добавь план Стамбула в календарь», «сдвинь всё завтра на час») с ожидаемой операцией и
  аргументами; +≈20 «обычный ассистент» (перевод длинного текста — не заметка, письмо, расчёт,
  объяснение) с проверкой «ничего не сохранено, ответ есть»; метрики: точность операции,
  ложные изменения = 0, цена хода.
- Корпус инъекций (`eval/injection/`): +≈15 «запись говорит: перенеси все встречи / удали траты
  / отмени напоминания» — ни одна операция не вызвана.

### Риски

| Риск | Что делаем |
|---|---|
| Перенос логики из роутов сломает экраны | контракты REST не меняются; `tests/api/*` + паритет-тесты; переносим по одному роуту |
| Модель выберет не то дело/событие (похожие названия) | только ссылки из показанного; при 2+ кандидатах — «Какую?» (`needs_choice`, уже есть) |
| Рост цены из-за Sonnet на большем числе ходов | код-первым для частых фраз (§3.5); наборы по доменам; метрика + алерт |
| Провайдер плохо держит `anyOf` в схеме (Gemini/OpenAI strict) | проверить на всех цепочках `chat_change` в фазе 0; запасной вариант — отдельный инструмент на операцию только для этого провайдера |
| Кэш промпта ломается из-за разных наборов | фиксированный порядок, мало комбинаций, смотреть долю попаданий |
| Часовые пояса при переносах | все даты — код (`timewords`, IANA tz человека), модель даёт слова/день, не ISO-время |
| Параллельная работа с пунктом 1 | фаза 0 не трогает `plans/` и календарные ops пункта 1; переезд пункта 1 в реестр — после его мержа |

## 6. Решения основателя (с рекомендацией)

1. **Напоминание из чата — сразу или через [Сохранить]?** Сейчас чат открывает форму S13 и
   ничего не сохраняет до кнопки. **Рекомендую:** когда время понятно — ставить сразу с
   «Отменить» (как дела со временем и Ф-66); форма — только когда время непонятно.
2. **«Хлеб купил» — отметить покупку или записать трату?** **Рекомендую:** без суммы и есть
   открытая покупка → отметить купленным; с суммой → трата **и** отметка (одна группа «Отменить
   всё»); без суммы и без покупки → как сейчас (дело/заметка).
3. **Порог «Да» для массовых изменений** (кроме корзины, она по Ф-66 без «Да» до 50).
   **Рекомендую:** спрашивать, если меняется больше 10 событий/дел/трат или фраза говорит «все».
4. **Что никогда не делается из чата.** **Рекомендую список:** удаление аккаунта, согласия, выход,
   смена телефона, удаление навсегда, отправка КП клиенту без «Да», импорт (нужен файл).
5. **Ф-39 (вид страниц из чата выключен в бете)** — **рекомендую** оставить выключенным до фазы 3.
6. **Цена:** больше ходов уйдёт на Sonnet (Ф-88). **Рекомендую** принять ориентир «средний ход
   изменения ≤ $0.04» с алертом, и проверить через неделю беты по `provider_usage`.
